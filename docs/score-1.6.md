# 추천점수 변경 안내 (1.6.0, 2026-11-18)

메뉴 추천 1단계(대표 메뉴 5개)의 추천점수 계산을 바꾸고, 2단계 가게 추천에 위치·거리 점수를 더했다. 이 문서는 무엇을, 왜, 어떻게 바꿨는지와 바꾼 뒤 측정 결과를 정리한다. DB·CSV 원본은 고치지 않았다. 점수 계산 코드만 바꿨다.

## 1. 왜 바꿨나

선택지 추천에서 고를 수 있는 모든 조합 22,140개(식단 4 × 영양 목표 3 × 맵기 3 × 국물 3 × 지역 5 × 선호 음식군 21 또는 이번 식사 음식군 20)를 돌려 확인했다.

- 선호 음식군을 하나로 고정하고 다른 조건을 바꾸면 결과는 충분히 바뀌었다. 80% 넘게 상위 5에 드는 "고정 메뉴"는 없었다.
- 하지만 **같은 조건이면 늘 똑같은 5개**가 나왔다. 점수에 무작위 요소나 "이미 본 메뉴" 개념이 없었다. 실제 사용에서 추천이 고정적으로 느껴지는 가장 큰 이유다.
- 점수에는 리뷰 수와 매장 수만 쓰고, 참고자료 DB에 있는 **리뷰 만족도(별점)와 단골 주문 비율은 쓰지 않았다**.

## 2. 점수 공식

| | 변경 전 (1.5.x) | 변경 후 (1.6.0) |
|---|---|---|
| 영양 적합도 N | 0.50 | 0.40 |
| 취향 일치 T | 0.35 | 0.30 |
| 리뷰 근거 E (리뷰 수·매장 수) | 0.15 | 0.10 |
| **리뷰 만족도 S (새로 추가)** | – | 0.12 |
| **단골 주문 R (새로 추가)** | – | 0.08 |
| 감점: 고른 맵기·국물을 확인할 수 없음 | 조건마다 15점 | 같음 |
| 감점: 선호 음식군 밖 | 25점 | 같음 |
| **감점: 최근 추천에 나온 음식 (새로 추가)** | – | 나온 횟수 × 10점, 최대 2번(20점) |

추천점수 = 100 × (0.40N + 0.30T + 0.10E + 0.12S + 0.08R) − 감점. 화면 순서는 지금처럼 추천점수 순서와 같다.

### 리뷰 만족도 S
- 출처: 참고자료 DB `pickmenu_data.current_menu_scores.rating` (매장 메뉴별 별점, 리뷰 내용 분석 만족도).
- 같은 컬럼(음식)의 매장 메뉴 별점을 **리뷰 수로 가중평균**한다.
- 고른 구에 그 음식 리뷰가 30건 이상이면 구 값을, 아니면 수원시 전체 값을 쓴다.
- 0~1 환산: `(별점 − 4.38) / (4.83 − 4.38)`, 범위 밖은 0 또는 1. 4.38·4.83은 추천 기준표의 별점 하·상 기준과 같다.

### 단골 주문 R
- 출처: 같은 표의 `repeat_ratio`(단골주문비율, 0.12~0.80, 평균 0.47).
- 별점과 같은 방법으로 리뷰 수 가중평균, 구 30건 기준을 쓴다.
- 0~1 환산: `(비율 − 0.30) / (0.65 − 0.30)`.

### 자료가 없을 때
- 만족도·단골 자료가 없는 음식은 감점하지 않고, 이번 후보들의 **중앙값**을 쓴다(영양 자료가 없을 때와 같은 방식).
- 음식과 컬럼은 기존 연결 규칙(정확히 같은 이름 → `·`로 묶인 이름 → 끝이 같은 가장 긴 이름)으로 맞춘다. 예: 순대국밥 → 국밥 컬럼.
- 측정 결과 상위 메뉴의 92.6%에 만족도·단골 자료가 있었다.

### 최근 추천 감점 (다양화)
- 브라우저가 최근 추천 3번의 대표 음식(최대 15개)을 기억해 추천 요청에 함께 보낸다. 이 브라우저에만 12시간 동안 저장하고 서버에는 저장하지 않는다.
- 서버는 그 음식이 최근에 나온 횟수만큼 10점씩(최대 2번) 깎는다. 메뉴 상세에 "최근 추천에 N번 나와 M점 감점"이라고 이유를 보여 준다.
- 10점은 선호 음식군 밖 감점(25점)보다 작다. 그래서 먼저 선호 음식군 안의 다른 메뉴가 올라온다.
- 결과 화면 아래에 **"다른 메뉴 보기 ↻"** 버튼을 추가했다. 같은 조건으로 다시 찾으면 방금 본 메뉴가 뒤로 가고 다른 메뉴가 올라온다.

## 3. 바꾼 뒤 측정 결과 (22,140조합, 일반·고기 식단에서 결과가 있는 9,744조합)

| 항목 | 결과 |
|---|---|
| 같은 조건에서 "다른 메뉴 보기"를 눌렀을 때 새로 올라온 메뉴 | 2번째 평균 2.8개 / 5, 3번째 또 2.6개 |
| 3번 볼 때 서로 다른 메뉴 수 | 평균 10.4개 (최대 15) |
| 2번째 결과가 첫 결과와 완전히 같은 비율 | 2.7% (선택지가 5개 이하인 좁은 조건) |
| 새 변수만으로(최근 감점 없이) 1위가 바뀐 조합 | 26.2% |
| 새 변수만으로 상위 5 구성이 바뀐 정도 | 평균 0.78개 |

- 감점 6점으로도 시험했다. 2번째에 새 메뉴가 2.1개만 나와 10점을 택했다.
- **점수 변수를 늘리는 것만으로는 다양성이 늘지 않았다.** 만족도·단골 주문은 조건과 관계없이 음식마다 정해진 값이다. 그래서 오히려 조건이 달라도 같은 음식이 앞에 서는 경향이 조금 생겼다(예: 선호 음식군 없음일 때 1위 종류 34 → 28). 대신 리뷰 평가가 좋은 메뉴가 앞에 오도록 **추천 품질**을 높이는 역할을 한다. 다양성은 최근 추천 감점이 맡는다.

## 4. 가게 추천(2단계)에 위치·거리 점수 추가

### 화면
- 위치는 **메뉴를 찾기 전 조건 화면**의 `배달 받을 위치`(지역 선택 아래)에서 고른다. 고르는 방법은 세 가지다.
  - 주소 검색: 도로명·지번 주소를 입력해 후보 중 하나를 고른다(네이버 Geocoding).
  - 지도(OpenStreetMap)를 직접 찍는다. Reverse Geocoding을 켜 두면 찍은 곳의 주소도 보여 준다.
  - `현재 위치 사용`.
- 고른 주소에 장안·권선·팔달·영통구가 있으면 `지역` 선택을 그 구로 자동으로 맞춘다.
- 위치는 로그인한 현재 페이지에서만 기억한다. 가게 추천에는 좌표만 보내며 서버는 주소와 좌표를 저장하거나 로그에 남기지 않는다.
- 가게 목록 위에는 고른 위치와 `위치 바꾸기` 버튼, 그리고 지도를 보여 준다. 지도에는 보이는 가게 10곳을 목록 번호와 같은 번호 핀으로, 고른 위치를 원으로 표시한다. 핀을 누르면 가게 이름·메뉴·리뷰 수·거리·주소가 나온다.
- 가게마다 도로명 주소와 `약 1.2km`처럼 거리를 보여 준다. 좌표가 없는 가게는 `거리 정보 없음`으로 보여 준다.

### 주소 검색 켜기 (서버)
- 서버의 환경변수 `PICKMENU_NAVER_MAPS_KEY`에 `naver-maps.key` 파일 경로를 지정한다(파일 권한 600). 지정하지 않으면 주소 검색 칸만 숨겨지고 나머지는 그대로 동작한다.
- 지도에서 찍은 위치의 주소 보기는 네이버 콘솔 Application 설정에서 **Reverse Geocoding**도 체크해야 한다.
- API: GET `/api/location/status`, JSON POST `/api/location/search`(2~80자의 `query`, 후보 5개), JSON POST `/api/location/address`(`lat`, `lng`). 로그인 세션이 필요하고, 서버 전체 1분 60회로 제한한다.

### 가게 점수
위치를 고르면 같은 메뉴 안의 가게 순서를 다음 점수로 정한다. 위치를 고르지 않으면 지금처럼 리뷰 수 순서다.

가게 점수 = 100 × (0.6 × 리뷰 점수 + 0.4 × 거리 점수)

| 항목 | 계산 |
|---|---|
| 리뷰 점수 | `log(1 + 이 가게 리뷰 수) / log(1 + 200)`, 최대 1 |
| 거리 점수 | 1km 이내 1, 5km 이상 0, 그 사이는 직선으로 줄인다 (배달 가능 거리를 생각한 값) |
| 좌표가 없는 가게 | 거리 점수 0.5(중간). 감점하지 않는다 |

거리는 고른 위치와 가게 좌표 사이의 직선 거리(하버사인)다. 실제 도로·배달 경로 거리는 아니다.

### 매장 좌표 만들기 (네이버 클라우드 Maps Geocoding)
- `07_지도데이터/픽메뉴_635매장_네이버API_재점검_통합.xlsx`에는 매장 635곳의 수집 주소만 있고 위도·경도는 0곳이다(이전 네이버 API 호출이 실행 환경 DNS 오류로 0회).
- 저장소의 `pickmenu/geocode_stores.py`가 주소를 좌표로 바꾼다.
  - 수집 주소에서 층·괄호를 지우고 찾는다. 못 찾으면 온라인 확인주소로 한 번 더 찾는다.
  - 같은 주소는 한 번만 호출한다(고유 주소 약 448개).
  - 원본 엑셀은 고치지 않는다.
- 결과는 같은 폴더의 `매장좌표_네이버.csv`(매장ID, 매장명, 사용 주소, API 도로명주소, 경도, 위도, 결과 상태, 확인 시각)에 쓴다. 실행할 때마다 `매장좌표_변환기록.md`에 건수를 남긴다.
- 서버는 환경변수 `PICKMENU_STORE_COORDS`에 지정한 이 CSV를 읽는다. 상태가 `OK`인 행만 쓰고, 파일이 바뀌면 다시 읽는다.
- 무료 이용량: 대표 계정 기준 Geocoding 월 300만 건이다. 이번 변환은 500건 안팎이다.

Windows CMD 실행 순서:
1. 네이버 클라우드 콘솔 → Maps → Application 등록에서 **Geocoding**을 체크하고 Client ID·Client Secret을 확인한다.
2. `07_지도데이터` 폴더에 `naver-maps.key` 파일을 만든다. 메모장으로 첫 줄에 Client ID, 둘째 줄에 Client Secret을 적는다. 이 파일은 공유하거나 커밋하지 않는다.
3. 시험 실행(5곳):

```bat
cd /d "D:\학교\3학년\캡스톤\pickmenu-dev\pickmenu"
python -X utf8 geocode_stores.py "D:\학교\3학년\캡스톤\픽메뉴_통합자료_20261115\07_지도데이터\픽메뉴_635매장_네이버API_재점검_통합.xlsx" --limit 5
```

4. `매장좌표_네이버.csv`에 좌표가 들어갔으면 `--limit 5` 대신 `--all`로 다시 실행한다. 이미 변환한 매장은 건너뛴다.
5. 다 되면 CSV를 서버로 옮기고 `PICKMENU_STORE_COORDS`를 지정한다.

## 5. 바뀐 파일

- `pickmenu/recommend.py`: 점수 가중치, `column_quality()`, `quality_parts()`, 최근 추천 감점.
- `pickmenu/menu_reco.py`: 참고자료에서 `repeat_ratio`를 함께 읽는다.
- `pickmenu/server.py`: `/api/recommend`가 `recent`(문자열 30개 이하, 각 40자 이하)를 받는다. 형식이 틀리면 400.
- `pickmenu/web/app.js`, `style.css`: 최근 추천 기억, "다른 메뉴 보기" 버튼, 안내 문구.
- `pickmenu/menu_stores.py`: 매장 좌표 읽기, 거리 계산, 가게 점수.
- `pickmenu/server.py`: `/api/recommend/stores`가 선택 항목 `location`(`{"lat", "lng"}`, 국내 범위)을 받는다. 지도 화면을 위해 CSP에 cdnjs(Leaflet 1.9.4, 무결성 해시 고정)와 OpenStreetMap 타일만 추가로 허용했다.
- `pickmenu/geocode_stores.py`: 매장 주소 → 좌표 변환 스크립트(새 파일).
- `pickmenu/naver_maps.py`: 주소 검색(Geocoding)·주소 보기(Reverse Geocoding), 호출 수 제한(새 파일).
- `pickmenu/server.py`: `/api/location/*` 주소 API, 위치 API 요청의 검색어를 접속 기록에서 지움.
- `pickmenu/web/index.html`: 조건 화면의 `배달 받을 위치` 칸, 주소 검색·지도 위치 고르기 창.
- `pickmenu/web/app.js`: 가게 목록 지도(번호 핀), 주소 표시, 지역 자동 선택.
- 테스트: `tests/test_score_variables.py` (만족도 가중평균, 점수 반영, 최근 감점, 요청 형식 검사), `tests/test_store_distance.py` (거리·가게 점수, 좌표 CSV 읽기, 위치로 순서 바뀜, 위치 형식 검사), `tests/test_naver_maps.py` (키 파일 형식, 응답 해석, 호출 제한). 모두 75개.
- 공유 배포본(`pickmenu-share/worker.js`)의 추천 계산은 이번에도 바꾸지 않았다. 로컬 서버와 결과가 다르다.
